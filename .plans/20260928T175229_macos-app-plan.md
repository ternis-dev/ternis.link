## 1. Mission

`dash.ternis.link` as a desktop citizen: a **regular dashboard application**
(dock icon, main window, Settings scene) that makes managing links **faster
than the browser** — native tables, charts, keyboard-first navigation — while
staying a thin client over the existing versioned API. No new server
endpoints in v1. Deliberately NOT a menu-bar app.

## 2. Goals / Non-Goals

Goals:

- Shorten anything (clipboard, selected text services, drag-drop) in < 2s.
- Full dashboard parity for daily tasks: links, analytics, QR, API keys,
  domains, notifications, activity, settings.
- Thoughtful native UX: sidebar navigation, keyboard-first, SF Symbols,
  Swift Charts, light/dark, VoiceOver labels, offline-tolerant caching.

Non-goals (v1):

- Admin console (`admin.ternis.link` stays web-only).
- Guest/anonymous shortening UI (API key or SSO required; guests keep href.nz).
- Windows/Linux ports (architecture must not forbid them, but they are not v1).

## 4. API Surface Used (all existing, `https://links.t-api.de/v1`)

- `GET /v1/` — version metadata (compat check, min-version gate).
- `POST /v1/links`, `GET /v1/links`, `GET/PUT/DELETE /v1/links/{link}`.
- `GET /v1/links/{link}/clicks`, `…/clicks/summary`, `…/qr?format=`.
- `GET/POST /v1/domains`, `GET/DELETE /v1/domains/{domain}`,
  `POST /v1/domains/{domain}/verify`.
- Auth: `Authorization: Bearer tl_…` (API key) — same scheme as the
  Chrome extension. Every response carries `API-Version`; honor `429` +
  `Retry-After`, surface `Deprecation`/`Sunset` when present.

## 6. UX Principles (the "thoughtful" part)

1. **Main window first**: sidebar navigation mirroring the dashboard
   (Links, API Keys, Domains, Activity, Notifications); `⌘1…⌘5` jump
   between sections, `/` focuses search.
2. **One global hotkey** (configurable, default `⌃⌥⌘L`) summons a
   quick-shortener panel from anywhere — the one floating element.
3. **Quiet by default**: dock icon optional;orter badge only for unread
   notifications; no polling storms (refresh on focus + manual).
4. **Trustworthy auth**: key lives in Keychain (never UserDefaults),
   copy-once display, one-click revoke, visible API-base setting.
5. **Offline-tolerant**: last-known links/analytics cached (SwiftData),
   writes queue with clear pending state.

## 8. Decisions (locked 2026-09-28)

1. **Stack: native SwiftUI.** SwiftPM package in `macos/` (no `.xcodeproj`;
   Xcode opens SwiftPM folders directly). Swift 6 strict concurrency,
   `async`/`await` URLSession, SwiftData cache, Swift Charts, MenuBarExtra.
   Minimum target macOS 14. Full Xcode install before M2 (Previews,
   archiving); M0–M1 build headless via `swift build` on CLT.
2. **Auth: API key + SSO OAuth.** Key first (M1, incl. "open api-keys page"
   assist); SSO via loopback (§10). Both credentials in Keychain; zero new
   server endpoints either way.
3. **Distribution: notarized DMG from ternis.link** (`Scripts/notarize.sh`
   via `notarytool`, `Scripts/dmg.sh` via `hdiutil`), + `/pages/macos`
   download page in M4 (same pattern as `/pages/extension`). Prerequisite:
   Apple Developer ID Application certificate.
4. **Machine facts**: dev Mac arm64, macOS 15.5, CLT-only + Swift 6.1.2.

## 9. Risks

- SSO-on-desktop complexity → mitigated by key-first auth, then loopback (§10).
- Scope creep toward admin features → explicitly out (§2).
- API drift → min-version gate on `GET /v1/` + `API-Version` checks.

## 10. SSO on Desktop (custom scheme, no server changes)

Key insight: our API already accepts **SSO access tokens as Bearer**
(`AuthenticateApi`: `tl_…` key *or* Ternis Auth token, userinfo-validated,
cached 5 min). The desktop app therefore talks to the **provider directly**
(`https://auth.ternis.net`) and never needs a server round-trip.

Transport is a **private-use URI scheme** (`ternislink://oauth/callback`,
RFC 8252 §7.1) rather than loopback: no ephemeral local HTTP server, no
port conflicts, no firewall prompts. Registered once at the provider
alongside the desktop `client_id` (public client + PKCE S256), and in the
app bundle's Info.plist (`CFBundleURLSchemes`).

1. App opens the system browser via `ASWebAuthenticationSession` to
   `{provider}/oauth/authorize` with the desktop client_id,
   `response_type=code`, PKCE S256, `redirect_uri=ternislink://oauth/callback`.
2. The scheme handler captures `?code=`, the app exchanges it at
   `{provider}/oauth/token` (+ `code_verifier`) for access + refresh tokens.
3. Tokens → Keychain. API calls use `Bearer <sso-access-token>` exactly like
   a `tl_…` key.
4. On 401: refresh via `grant_type=refresh_token` → retry once → else prompt
   re-login (same UX as `RefreshSsoToken` logout on web).
5. Logout: wipe Keychain entry; optional RP-initiated logout in browser.

Credential model: `.apiKey(String)` or `.sso(access, refresh, expiry)` enum;
`APIClient` is agnostic, `AuthManager` owns refresh. Sequencing: M1 ships
key auth; SSO lands with M3 settings (login screen offers both from day one
in UI copy, SSO button enabled when the desktop client_id is configured).
